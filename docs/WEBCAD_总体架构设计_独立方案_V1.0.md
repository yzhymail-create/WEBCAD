# WEBCAD 总体架构设计（独立方案）

- 文档版本：V1.1
- 日期：2026-11-22
- 状态：架构建议稿，供评审；不替代《框架与接口规格》
- 设计定位：当前先搭建独立的网页版 2D 图纸生成与后处理工具，同时为未来专业模块预留清晰扩展接口。
- 参考思想：借鉴 CHS 的模块化、数据中心化、专业流程分工和工程发布思想；不照搬其完整产品范围。

---

## 0. 核心结论

WEBCAD 当前阶段**不接入 3D，不依赖 CATIA，不承担 3D 到 2D 的转换**。

当前要做的是一个独立的 Web 2D 图纸工具：

1. 在浏览器中创建和管理二维图纸；
2. 通过简单数据输入、图形对象和模板生成图纸；
3. 对图纸进行选择、绘制、移动、修改、标注等操作；
4. 对图纸进行整理、属性处理和基础检查；
5. 输出可继续编辑和使用的工程文件，例如 DXF，以及按实际需要提供 PDF、数据报表。

同时，架构不能把未来封死。未来可能增加的零件库、原理图、电气数据管理、3D/MCAD 数据接口、自动化规则、协同和 PLM 集成，应通过模块边界和数据契约预留接入位置。

**当前只实现必要能力；未来扩展先预留接口和边界，不提前开发复杂功能。**

## 1. 产品范围

### 1.1 当前阶段（必须实现）

| 能力 | 当前范围 |
|---|---|
| Web 工作台 | 浏览器打开、工具栏、图纸画布、对象/属性面板、状态栏 |
| 工程与图纸 | 新建、打开、保存、另存为、图纸/页面管理 |
| 图纸生成 | 基于简单输入、图形对象、模板生成二维图纸 |
| 图形编辑 | 选择、绘制、移动、复制、删除、旋转、连接、对齐 |
| 后处理 | 文字、尺寸/标注、图层、颜色/线型、对象属性、图框和标题栏 |
| 数据管理 | 图纸对象结构化保存、对象 ID、属性与引用关系 |
| 基础检查 | 对象属性完整性、连接关系、重复/重叠等可定义规则 |
| 工程输出 | DXF 为主要目标；PDF、CSV/Excel 根据实际需要安排 |
| 操作体验 | 撤销/重做、缩放、平移、捕捉、选择过滤、快捷操作 |

“简单图纸生成”首期以可控、可验证的二维对象为主，不承诺自动完成完整汽车线束电气设计。

### 1.2 当前明确不做

- 不接入 CATIA 或其他 3D 建模软件；
- 不解析 STEP/STP，不处理三维线束模型；
- 不做 3D 拓扑提取、三维布线和 3D 到 2D 展开；
- 不要求输入 topology.json 或 layout.json 才能使用；
- 不实现完整电气原理图设计和逻辑-物理集成；
- 不建设多人实时协同、企业权限、PLM 或云端任务平台；
- 不为尚未验证的未来需求提前引入微服务、复杂数据库或 DLL。

### 1.3 未来可扩展方向（当前只预留）

- Library：连接器、端子、附件、符号、图框和模板库；
- Harness Data：导线、线号、连接器、端子及线束工程属性管理；
- Logic：电气原理图和电气连接关系；
- Integrator：逻辑数据与物理线束数据关联；
- 3D / MCAD Connector：从外部三维系统导入或同步数据；
- Automation：批量生成、规则驱动和脚本扩展；
- Collaboration：用户、权限、评审、版本和协同；
- PLM / ERP / MES Connector：企业系统数据交换。

这些是扩展插槽，不是当前开发任务。是否启用、何时启用，取决于实际需求。

## 2. 架构原则

1. **二维图纸是当前核心。** 当前业务模型围绕 Drawing、Sheet 和二维图形对象组织，不围绕 3D 拓扑组织。
2. **数据与显示分离。** 图纸对象数据不等于 SVG/Canvas 的显示节点；更换渲染方式不能导致工程数据丢失。
3. **编辑器与生成器分离。** 自动生成图纸和人工修改图纸使用同一套对象模型，但职责分开。
4. **工程对象与输出格式分离。** DXF 是导出格式，不应成为编辑器唯一的数据源。
5. **模块通过稳定接口协作。** 不直接依赖其他模块的页面 DOM、内部变量或私有实现。
6. **ID 稳定、属性明确。** 每个工程对象有唯一 ID；单位、坐标、图层和对象类型有明确约定。
7. **可撤销、可追溯。** 用户操作形成命令或变更记录，支持撤销/重做和必要的版本恢复。
8. **先做单机可用，再服务化。** 首期优先浏览器本地运行和本地文件保存；多人协同和云服务以后再评估。
9. **扩展点先定义，不做空壳系统。** 只建立必要接口、注册机制和数据版本策略，不提前实现尚无用例的模块。
10. **工程输出必须可验证。** 导出后检查图层、实体、单位、坐标和属性，不能只以“文件生成成功”作为验收。

### 3.1 分层职责

| 层 | 职责 | 边界 |
|---|---|---|
| Web 工作台 | 页面布局、工具入口、用户交互流程 | 不直接实现图纸几何和 DXF 业务 |
| 业务模块 | 工程管理、生成、编辑、检查、输出 | 通过领域模型和接口读写数据 |
| 领域模型 | 定义图纸对象、属性、关系、约束 | 不依赖 SVG、Canvas 或 DXF 实体 |
| 数据契约 | 定义保存格式、模块接口和版本 | 不保存页面临时状态 |
| 图形/文件适配 | 渲染、几何计算、文件读写 | 不擅自改变工程对象含义 |
| 基础设施 | 本地存储、日志、测试、配置 | 不承担专业业务判断 |

## 4. 业务模块规划（参考 CHS 的模块化思想）

模块是代码和职责边界，首期可以在同一个 Web 应用中运行，不需要拆成多个服务。

| 编号 | 模块 | 当前/未来 | 主要职责 |
|---|---|---|---|
| M0 | Project 工程管理 | 当前 | 新建、打开、保存、另存为、工程文件组织 |
| M1 | Drawing 图纸管理 | 当前 | 图纸、图框、页面、比例、单位、标题栏 |
| M2 | Data / Domain 数据模型 | 当前 | 二维对象、属性、ID、引用关系和数据校验 |
| M3 | Generator 图纸生成 | 当前 | 根据输入数据、模板和规则创建图纸对象 |
| M4 | Editor 二维编辑器 | 当前 | 选择、绘制、移动、复制、删除、旋转、对齐 |
| M5 | PostProcess 图纸后处理 | 当前 | 标注、文字、图层、属性、图框和图面整理 |
| M6 | Validation 基础检查 | 当前 | 数据完整性、几何问题、连接关系和输出检查 |
| M7 | Publish 工程输出 | 当前 | DXF 导出；按需求扩展 PDF 和报表 |
| M8 | Library 零件/符号/模板库 | 预留 | 连接器、端子、符号、附件、图框和模板 |
| M9 | Harness Data 线束工程数据 | 预留 | 导线、线号、连接器、端子及线束属性 |
| M10 | Logic 原理图 | 预留 | 电气器件、端子和电气连接关系 |
| M11 | Integrator 数据集成 | 预留 | 原理图、线束数据与物理数据关联 |
| M12 | 3D / MCAD Connector | 预留 | 外部三维数据导入、映射和同步 |
| M13 | Automation 自动化 | 预留 | 批处理、规则引擎、用户脚本和自动生成 |
| M14 | Collaboration 协同 | 预留 | 用户、权限、评审、版本和协同编辑 |
| M15 | Enterprise Connector | 预留 | PLM、ERP、MES 等外部系统接口 |

**实施约束：** 当前模块必须有真实功能；预留模块只定义边界和接口位置，不创建没有实际用途的大量空文件、空页面或空服务。

## 5. 当前核心领域模型

当前以二维图纸为中心，建议至少包含以下对象：

| 对象 | 含义 | 典型字段 |
|---|---|---|
| Project | 工程项目 | project_id、name、revision、created_at |
| Drawing | 一份图纸 | drawing_id、name、unit、scale、sheet_ids |
| Sheet | 图纸页面/工作区 | sheet_id、width、height、orientation |
| Entity | 通用二维图形对象 | entity_id、type、layer_id、geometry、attributes |
| Layer | 图层 | layer_id、name、visible、locked、style |
| Block | 可复用组合对象 | block_id、name、base_point、entities |
| Symbol | 专业符号实例 | symbol_id、library_ref、position、rotation |
| Text | 文字对象 | entity_id、content、position、height、style |
| Dimension | 尺寸/标注对象 | entity_id、definition、text_override、style |
| Constraint | 对象间约束 | constraint_id、type、entity_refs、parameters |
| Operation | 用户操作记录 | operation_id、command、target_ids、before、after |

首期图形实体建议支持：Line、Polyline、Arc、Circle、Rectangle、Text、Dimension、BlockReference。具体对象类型以实现和 DXF 兼容性评估为准。

### 5.1 通用对象约定

每个 Entity 至少应有：
- 稳定的 entity_id；
- 明确的 type；
- 所属 layer_id；
- 几何定义 geometry；
- 可扩展 attributes；
- 必要时的 block/library 引用；
- 创建和修改信息（首期可简化）。

图形坐标采用统一的工程坐标系，内部长度单位建议毫米。屏幕像素只用于显示变换，不得写回工程几何作为真实尺寸。

### 5.2 专业对象扩展

未来连接器、端子、导线等对象不应通过不断增加通用 Entity 的特殊字段来硬塞。应由专业数据模块定义对象，再通过稳定引用与二维 Symbol / Block / Entity 关联。

例如未来 Connector 可以引用一个图纸 Symbol 实例；未来 Wire 可以引用二维图形表达。专业对象数据与其图面表达保持分离。

## 7. 数据契约与工程文件

### 7.1 首期工程包建议

```
project/
├── project.json
├── manifest.json
├── drawings/
│   ├── main.drawing.json
│   └── detail.drawing.json
├── assets/
│   ├── images/
│   └── attachments/
├── templates/
│   └── drawing-template.json
├── validation/
│   └── validation-report.json
├── publish/
│   ├── drawing.dxf
│   └── publish-manifest.json
└── history/
    └── operations.json
```

实际首期可以先将工程保存为单个 JSON 文件或浏览器本地文件；目录结构是逻辑组织建议，不要求一开始实现复杂文件包。

### 7.2 数据契约原则

1. 每个 Project、Drawing、Sheet、Entity、Layer 和 Block 均有稳定 ID。
2. schema_version 与应用版本分开管理。
3. 坐标单位、图纸单位、比例和角度单位必须明确声明。
4. 页面显示状态（缩放、选中、高亮、面板开关）与工程几何数据分离。
5. 未知字段在读取和保存时应尽可能保留，避免未来扩展字段被旧版本无意丢弃。
6. 破坏性数据结构变更必须提升 schema_version，并提供迁移策略。
7. 用户编辑应形成命令或变更记录，支持撤销/重做。
8. 模块间通过对象 ID 和引用建立关系，不以显示名称作为唯一关联依据。
9. 导出文件应记录来源 drawing_id、revision 和输出配置。
10. 自动生成和人工修改的数据应能区分；重新生成不得无提示覆盖用户编辑。

### 7.3 扩展接口预留

建议预留少量稳定接口类别，而不是提前实现全部未来功能：

- Generator Provider：注册不同图纸生成器；
- Entity Type Registry：注册专业图形对象类型；
- Library Provider：提供符号、零件和模板；
- Import / Export Adapter：接入新的文件格式或外部数据源；
- Validation Rule Registry：注册新的检查规则；
- Command Registry：注册编辑命令和快捷操作；
- Project Metadata Extension：允许未来专业模块附加工程元数据。

接口应有版本和能力声明。首期只实现当前确实需要的 Provider；未来模块接入时再实现对应适配器。

## 8. Web 技术实现建议

### 8.1 首期建议

| 部分 | 建议 | 说明 |
|---|---|---|
| 页面与交互 | HTML + CSS + JavaScript | 先保持轻量，代码模块化 |
| 二维渲染 | SVG 优先 | 适合对象选择、属性关联和矢量输出 |
| 高性能渲染 | Canvas 作为未来选项 | 对象数量显著增长后再评估 |
| 几何模型 | 独立 JavaScript 模块 | 不与 SVG DOM 结构绑定 |
| 数据格式 | JSON | 易于检查、导入、导出和版本迁移 |
| 文件输出 | 独立 DXF Adapter | DXF 结构不渗透到编辑器内部 |
| 本地保存 | 浏览器文件能力 / 下载上传 | 以目标浏览器兼容性实测为准 |
| 后端 | 首期可无后端 | 单机浏览器可完成核心流程 |
| 自动化测试 | 几何单元测试 + 浏览器交互测试 | 关键编辑和导出场景必须回归 |

SVG 是首期推荐，不是永久绑定。只要领域模型不依赖 SVG 元素，将来可以更换渲染引擎。

### 8.2 DLL、Python 和服务端

当前不需要 DLL，也不要求 Python 作为网页运行前提。若后续出现复杂几何计算、批处理或复用既有 Python 工具的实际需求，再通过明确的本地服务/API 或命令行适配器接入。

只有在有原生 SDK、性能瓶颈或多个原生程序复用等明确理由时，才评估 DLL。

## 10. 质量与测试策略

| 测试类别 | 典型测试 | 验收重点 |
|---|---|---|
| 数据模型 | ID 唯一、引用完整、未知字段保留 | 数据可稳定保存和重载 |
| 几何计算 | 坐标变换、长度、角度、相交、捕捉 | 计算值正确、单位一致 |
| 编辑器 | 选择、移动、复制、删除、撤销重做 | 操作结果和历史一致 |
| 生成器 | 模板生成、参数变化、对象数量 | 输入相同则结果可重复 |
| 后处理 | 图层、文字、尺寸、属性 | 不破坏原对象关系 |
| DXF 输出 | 图层、实体、块、文字、单位 | 在目标 CAD 中可打开并继续编辑 |
| 文件往返 | 保存、关闭、重新打开、再次导出 | 数据无丢失、无无意变化 |
| 回归 | 已确认的示例图纸 | 修改后不破坏既有能力 |

所有关键功能应有最小测试样例。用户发现的真实问题要转化为可重复的回归测试。

## 11. 分阶段实施路线

### P0：框架与最小可运行工作台

- 建立 Web 页面框架；
- 建立画布、工具栏、对象/属性面板和状态栏；
- 建立 Project、Drawing、Sheet、Entity 基础模型；
- 实现 JSON 保存和重新打开；
- 确立模块接口、ID、单位和坐标约定。

交付：可以新建、绘制、保存、重新打开的最小网页工作台。

### P1：基础图形生成和编辑

- 基础图元绘制；
- 选择、移动、复制、删除、旋转；
- 缩放、平移、捕捉和对齐；
- 撤销/重做；
- 简单模板和参数化生成。

交付：可以完成简单二维图纸的生成与编辑。

### P2：图纸后处理

- 图层管理；
- 文字、尺寸和标注；
- 图框、标题栏；
- 对象属性编辑；
- 图面整理和基础检查。

交付：具备基本工程表达能力的二维图纸。

### P3：工程输出和稳定性

- DXF 导出；
- 必要的 PDF/报表；
- 输出回读检查；
- 工程文件版本和恢复；
- 典型图纸回归测试。

交付：可以输出并在常用 CAD 软件中继续编辑的图纸。

### P4：专业功能扩展（按需求启动）

- 符号和零件库；
- 导线、连接器、端子等线束工程数据；
- 面向线束的自动生成规则；
- 电气原理图和逻辑数据；
- 外部 3D/MCAD 数据接口。

### P5：服务化和企业集成（按需求启动）

- 云端项目存储；
- 多人协同、权限和评审；
- 自动化任务服务；
- PLM / ERP / MES 接口。

## 12. 当前阶段验收标准

当前阶段完成的判断标准：

1. 浏览器能够打开 WEBCAD 工作台；
2. 用户能够创建工程和二维图纸；
3. 能够创建和编辑基本二维图形对象；
4. 图纸对象有稳定 ID、图层和属性；
5. 能够保存、关闭并重新打开工程，数据不丢失；
6. 能够完成基本文字、标注、图层和属性后处理；
7. 能够执行基础检查并定位问题对象；
8. 能够导出至少一种可在目标 CAD 中继续编辑的二维文件（优先 DXF）；
9. 生成、编辑、保存和导出职责分离，关键模块不互相耦合；
10. 当前代码中不存在对 3D/CATIA 数据的强制依赖。

## 13. 需要在实施前确认的事项

以下项目以实际试做和用户确认结果为准，不在架构文档中擅自定死：

| 项目 | 当前建议 | 待确认内容 |
|---|---|---|
| 主要图形表达 | SVG | 目标图纸规模和交互性能 |
| 工程文件格式 | JSON 工程数据 | 单文件还是 ZIP 工程包 |
| 输出格式 | DXF 优先 | DXF 版本、图层和块属性标准沿用现有规格的哪些部分 |
| 图纸生成入口 | 模板 + 简单数据 + 手动绘制 | 首期具体生成对象和输入表结构 |
| 保存方式 | 浏览器本地文件 | 目标浏览器及本地文件权限限制 |
| 专业对象 | 通过 Symbol/Block 和专业数据引用扩展 | 首期是否需要连接器、导线等对象 |
| 后端 | 暂不需要 | 何时出现多用户、远程存储或批处理需求 |
| 扩展接口 | Provider / Registry | 先实现哪些最小接口，避免过度抽象 |

## 14. 与现有《框架与接口规格》的关系

两份文档承担不同职责：

- 《框架与接口规格》：记录已有代码、数据、页面、DXF 约定和具体接口需求，属于现状与详细规格。
- 本文《总体架构设计》：明确当前产品范围、模块边界、数据模型、技术路线和后续扩展方式，属于目标架构建议。

发生冲突时：
1. 已经实测且仍然有效的代码行为和文件标准，需要在实施时核实后保留；
2. 用户明确确认的需求优先于本文建议；
3. 本文的未来扩展模块不构成当前必须实现的功能；
4. 不得为了适配旧的 3D 转 2D 方案，把 3D 数据接入重新变成当前前提；
5. 修改数据契约时同步更新测试和接口文档。

## 15. 最终建议

WEBCAD 当前要先成为一个简单、稳定、可扩展的网页版二维图纸工具。

当前开发顺序应是：

**工作台框架 → 二维数据模型 → 图纸生成 → 图形编辑 → 后处理 → 基础检查 → DXF 输出。**

未来扩展顺序则由真实需求决定：

**符号/零件库 → 线束专业数据 → 原理图/逻辑 → 3D/MCAD 接口 → 自动化与协同 → 企业系统集成。**

不要把未来的复杂能力提前塞进当前版本，也不要因为当前只做简单二维图纸，就把数据模型、模块边界和扩展接口做成无法演进的单体程序。

这就是本方案的核心取舍：**当前范围保持轻量，底层架构保持开放，扩展能力按需逐步启用。**
