# WEBCAD 总体架构设计（独立方案）

- 文档版本：V1.0
- 日期：2026-11-22
- 状态：架构建议稿，供评审；不替代《框架与接口规格》
- 设计依据：现有 WEBCAD 框架与接口规格、已存在的 topology.json / layout.json / Python 展开与 DXF 导出流程 / SVG 查看器，以及 CHS 的模块化工程流程思想
- 设计目标：先形成可验证的 3D 线束拓扑到 2D 工程图闭环，再逐步扩展为可维护、可扩展的线束工程平台

---

## 0. 先说结论

WEBCAD 不应被设计成一个单体网页绘图程序，也不应一开始就复制 CHS 的完整产品体系。

更合理的定位是：

> **以线束工程数据为中心，以拓扑和几何计算为核心，以 2D 排板为首个可交付工作台，以规则校验和制造输出形成工程闭环的模块化平台。**

CHS 值得借鉴的不是界面或模块名称，而是它的工程组织方式：

- 不同专业阶段有明确职责；
- 模块之间通过稳定的数据契约交接；
- 上游数据与下游制造表达分开；
- 设计过程和发布过程有明确的校验关口；
- 后续可接入零件库、原理图、MCAD、PLM，而不必推翻已有核心。

WEBCAD 当前应优先做好 3D 拓扑、2D 布局、编辑、DRC、DXF/报表五个环节。项目管理、原理图、拓扑匹配、零件库、协同和 PLM 先定义接口，不作为首期开发前提。

## 1. 产品边界与设计原则

### 1.1 产品定位

WEBCAD 是一个面向汽车线束工程的数字化设计与交付平台。首期处理已经从 CATIA 等来源获得的线束三维拓扑数据，将其转换为可编辑、可校验、可追溯的二维线束排板图，并输出 CAD 工程文件和数据报表。

首期不负责：
- 三维线束建模和三维布线；
- 电气原理图设计；
- 自动决定整车电气架构；
- 替代 CATIA 等 MCAD 工具；
- 企业级 PLM、权限体系和多人实时协同。

### 1.2 八条架构原则

1. **工程数据优先于图形。** 图形是数据的表达，不是工程事实的唯一载体。
2. **拓扑真值与二维布局分离。** 编辑二维图不得悄悄修改三维拓扑或三维长度。
3. **物理对象与工程路径分离。** 管段、分支、节点、走线、连接器到连接器的路径是不同概念，不能混为一谈。
4. **模块只通过契约交接。** 模块不依赖其他模块的内部变量、私有算法或页面 DOM。
5. **计算可重复。** 同一输入、同一规则版本应得到可复现的结果；关键计算应记录版本和参数。
6. **校验独立于生成。** 不能只相信布局引擎自己报告的结果；DRC 应从输出几何和源拓扑独立复算。
7. **先离线单机，后服务化。** 首期本地文件可完成导入、计算、编辑、校验、导出；后续再接账号、项目和云端存储。
8. **先验证再抽象。** 不为了未来可能出现的需求提前建设复杂框架；每个扩展点都要有真实用例再实现。

## 2. 总体分层架构

建议采用六层结构。层与层之间通过明确的数据对象或接口通信。

```
┌──────────────────────────────────────────────────────────┐
│                    6. 工程工作台 / 应用层                  │
│ 项目入口｜数据导入｜2D排板｜查看定位｜校验报告｜工程发布     │
├──────────────────────────────────────────────────────────┤
│                    5. 专业业务模块层                       │
│ 3D拓扑处理｜布局计算｜2D编辑｜DRC｜DXF/报表｜零件库(后续)   │
├──────────────────────────────────────────────────────────┤
│                    4. 领域模型与规则层                     │
│ Project / Harness / Node / Segment / Branch / Route       │
│ 几何规则｜拓扑规则｜命名规则｜长度口径｜版本规则             │
├──────────────────────────────────────────────────────────┤
│                    3. 工程数据契约层                       │
│ topology.json｜layout.json｜drc-report.json｜project.json  │
│ library.json(后续)｜schematic.json(后续)｜manifest.json     │
├──────────────────────────────────────────────────────────┤
│                    2. 计算与适配层                         │
│ Python计算核心｜图算法｜几何算法｜JSON适配｜DXF适配         │
│ Web前端渲染｜本地文件适配｜未来服务/API适配                 │
├──────────────────────────────────────────────────────────┤
│                    1. 基础设施层                           │
│ 文件系统｜版本记录｜日志｜测试数据｜自动化测试｜打包部署     │
└──────────────────────────────────────────────────────────┘
```

### 2.1 分层职责

| 层 | 主要职责 | 不应承担的职责 |
|---|---|---|
| 应用层 | 组织用户操作、页面和工作流程 | 不直接实现拓扑/几何核心算法 |
| 专业业务模块层 | 完成具体工程任务 | 不随意读写其他模块内部状态 |
| 领域模型与规则层 | 定义工程对象、对象关系和计算口径 | 不依赖网页控件或 DXF 实体 |
| 工程数据契约层 | 定义模块间长期稳定的数据格式 | 不塞入某个页面专用的临时状态 |
| 计算与适配层 | 执行算法、连接文件格式和运行环境 | 不决定工程业务规则 |
| 基础设施层 | 文件、日志、测试、部署和版本管理 | 不包含线束专业判断 |

## 3. 参考 CHS 的业务模块划分

建议将 WEBCAD 组织为以下模块。模块是业务边界，不要求首期都做成独立进程或独立服务。

| 编号 | WEBCAD 模块 | CHS 思想对应 | 首期状态 | 核心职责 |
|---|---|---|---|---|
| M0 | Project 工程管理 | Project | 轻量实现 | 工程文件、来源、版本、任务状态 |
| M1 | Data / Domain 数据中心 | 统一数据模型 | 首期核心 | 读取、索引、关联、版本和数据完整性 |
| M2 | Topology 拓扑处理 | HarnessXC 的拓扑基础 | 首期核心 | 节点、管段、分支、连接关系和路径分析 |
| M3 | Layout 二维布局引擎 | Formboard 前置 | 首期核心 | 三维拓扑到二维布局的计算与优化 |
| M4 | Formboard 二维排板工作台 | Formboard | 首期核心 | 2D 查看、编辑、标注、图层和交互 |
| M5 | DRC 工程校验 | correct-by-construction | 首期核心 | 独立检查拓扑、几何、长度和输出完整性 |
| M6 | Publish 工程发布 | Publish | 首期核心 | DXF、Excel、检查报告和发布包 |
| M7 | Library 零件与符号库 | Library / Symbol | 预留接口 | 连接器、端子、卡扣、符号及属性 |
| M8 | Logic 原理图 | Logic | 未来扩展 | 电气连接、器件、端子和导线逻辑 |
| M9 | Integrator 逻辑-物理集成 | Integrator | 未来扩展 | 原理图与三维物理拓扑的匹配和差异管理 |
| M10 | MCAD / PLM Connector | MCAD / PLM | 未来扩展 | CATIA、PLM 等外部系统数据交换 |
| M11 | Collaboration 协同服务 | Project / PLM 扩展 | 未来扩展 | 用户、权限、版本、评审和多人协作 |

说明：首期可在一个程序中实现多个模块，但代码目录、输入输出和职责必须分开。不要为了“微服务化”增加部署复杂度。

## 4. 核心工程对象：先统一概念

这是整个系统最重要的基础。对象名称和含义必须稳定，否则后续路径计算、编辑、DRC 和报表会各自形成一套口径。

### 4.1 对象定义

| 对象 | 含义 | 典型属性 |
|---|---|---|
| Project | 一个工程或一次交付任务 | project_id、名称、来源、版本 |
| Harness | 一套线束或一个线束总成 | harness_id、名称、配置 |
| Node | 拓扑节点 | node_id、类型、坐标、外部实体名 |
| Segment | 两个拓扑节点之间的物理线段 | segment_id、起终节点、长度、所属实体 |
| Branch | CATIA 中的物理分支/管段对象 | branch_id、实体全名、直径、中心线、长度 |
| Route | 按工程定义连接两个端点的一条连续路径 | route_id、起终端、组成 Segment 列表、路径长度 |
| Connector | 连接器或电气接口实体 | connector_id、零件号、端子信息 |
| LayoutPath | Route 或物理路径在二维图上的表达 | layout_id、点列、分段、二维长度 |
| Annotation | 二维图上的文字、尺寸或工程标记 | annotation_id、类型、位置、内容 |
| DRCResult | 某一规则版本对某一数据版本的检查结果 | rule_id、状态、对象引用、证据 |

### 4.2 特别重要：Branch、Segment、Route 不得混用

- **Branch** 是源三维模型中的物理分支对象，不代表一定是连接器到连接器的完整路径。
- **Segment** 是拓扑图中的基本连接边，具有明确的起点和终点。
- **Route** 是从一个工程端点到另一个工程端点的连续路径，可能由多个 Segment、多个 Branch 组成，也可能经过中间节点。

因此：
- 不能把“最长 Branch”当成“最长连接器到连接器路径”；
- 不能只按单根管子的长度判断分支长度；
- Route 长度应由其组成的有效 Segment 按规则汇总；
- 对有环拓扑，必须明确路径搜索策略、端点规则和环路处理规则，不能简单地对任意图求一个所谓最长路径。

路径分析应明确区分：
1. 连接器到连接器的完整路径；
2. 连接器到末端节点的路径；
3. 从主干分叉出去的支路；
4. 拓扑图中的环路；
5. 仅用于几何表达、并不改变电气连通关系的中间过路点。

具体路径口径以工程需求和实测数据为准，不能仅凭字段名推断。

## 5. 核心数据流与工程闭环

### 5.1 首期主流程

```
外部3D数据 / 已有拓扑数据
          │
          ▼
    M1 数据导入与检查
          │
          ▼
    topology.json（源拓扑快照）
          │
          ▼
    M2 拓扑分析与路径识别
          │
          ▼
    M3 二维布局计算
          │
          ▼
    layout.json（布局版本）
          │
          ▼
    M4 二维查看与人工编辑
          │
          ▼
    layout.json（编辑版本）
          │
          ├──────────────┐
          ▼              ▼
    M5 独立DRC       M4 只读预览
          │
      通过 / 失败
          │
          ▼
    M6 发布前复核
          │
          ▼
    DXF + Excel + DRC报告 + 工程清单
```

### 5.2 各阶段必须有明确产物

| 阶段 | 输入 | 输出 | 完成条件 |
|---|---|---|---|
| 导入 | 原始文件或 topology.json | 标准化拓扑快照 | 数据结构完整、ID 唯一、引用有效 |
| 拓扑分析 | topology.json | 路径/连通分析结果 | 节点、边、连通分量和路径口径明确 |
| 布局 | topology.json + 布局参数 | layout.json | 所有要求表达的对象均有布局结果 |
| 编辑 | layout.json | 新的布局版本 | 编辑记录可追踪，源拓扑不被改写 |
| 校验 | topology.json + layout.json + 规则集 | drc-report.json | 每条规则有结果和证据 |
| 发布 | 已通过校验的布局版本 | DXF、报表、发布清单 | 文件回读检查通过，发布包可追溯 |

## 6. 数据契约与文件组织

### 6.1 首期建议文件

```
project/
├── project.json             # 工程基本信息、文件引用、当前版本
├── manifest.json            # 本次工程包文件清单、哈希和生成信息
├── source/
│   └── topology.json        # 原始拓扑快照，只读
├── analysis/
│   └── route-analysis.json  # 路径分析结果，可重算
├── layout/
│   ├── layout.json          # 当前布局
│   └── layout-history/      # 可选的布局历史快照
├── validation/
│   ├── drc-rules.json       # 本次使用的规则集版本
│   └── drc-report.json      # 校验结果与证据
├── publish/
│   ├── drawing.dxf
│   ├── report.xlsx
│   └── publish-manifest.json
└── logs/
    └── operation.log
```

此目录是建议结构，不要求立即迁移现有文件。可先用现有文件名和路径，逐步增加 manifest 和报告。

### 6.2 数据文件职责

| 文件 | 数据性质 | 谁能写 | 谁能读 |
|---|---|---|---|
| topology.json | 源数据快照 | 导入/拓扑适配器 | 拓扑、布局、DRC、报表 |
| route-analysis.json | 可重算分析结果 | 拓扑分析模块 | 布局、查看、DRC |
| layout.json | 二维布局及编辑结果 | 布局引擎、编辑器（通过版本化写入） | 查看、DRC、导出 |
| drc-report.json | 校验证据 | DRC 模块 | 用户、发布模块 |
| library.json | 零件库数据 | Library 模块 | 编辑、报表、发布 |
| schematic.json | 原理图数据 | Logic 模块 | Integrator、报表 |
| manifest.json | 文件清单与版本关系 | 工程管理/发布模块 | 所有模块 |

### 6.3 数据契约规则

1. 所有工程对象必须有稳定 ID；显示名称不能充当唯一 ID。
2. 单位必须显式声明；内部长度统一使用毫米，角度统一声明单位。
3. 坐标系必须声明来源、轴向和变换关系；禁止默认假设不同来源的坐标系一致。
4. 字段新增优先于字段改名或改义；破坏性变更必须提升 schema_version。
5. 每份结果应记录输入文件哈希、算法版本、规则版本和关键参数。
6. 可重算数据与人工编辑数据必须可区分；重新运行布局引擎不得无提示覆盖人工修改。
7. 缺字段、未知枚举、引用丢失应产生明确错误，不应静默填充可能改变工程含义的默认值。
8. 所有 ID 引用必须可解析；发布前必须验证引用完整性。

### 6.4 版本概念必须分开

- schema_version：数据格式版本；
- algorithm_version：计算算法版本；
- rule_set_version：DRC 规则版本；
- project_revision：工程修订版本；
- layout_revision：布局修订版本；
- source_hash：源拓扑内容指纹。

现有 meta.version 若表示生成器版本，应继续保留其原意，不要把它改造成 schema_version。

## 7. 关键模块设计

### 7.1 M1 数据中心与导入

职责：
- 读取现有 topology.json 和 layout.json；
- 检查 JSON 结构、必需字段和引用关系；
- 建立按 node_id、segment_id、branch_id、route_id 查询的索引；
- 保留原始字段和未知扩展字段；
- 生成数据摘要、导入报告和来源信息。

不负责：
- 重新计算布局；
- 自动修改源数据；
- 直接生成 DXF。

建议提供统一接口概念：
- load_topology()
- validate_topology()
- index_topology()
- load_layout()
- validate_layout()
- save_layout_revision()

具体函数签名由现有代码适配后再确定。

### 7.2 M2 拓扑与路径分析

职责：
- 建立图结构：Node 为顶点，Segment 为边；
- 处理 Branch 与 Segment 的映射；
- 计算连通分量、节点度数、端点和分支关系；
- 识别连接器到连接器、连接器到末端等路径；
- 保留环路、并行边和多重关系，不可在建图时随意丢弃；
- 输出可追溯的路径组成清单。

要求：
- 路径必须能追溯到原始 Segment 和 Branch；
- 路径长度由组成边计算，不能只读取未经验证的汇总字段；
- 同一拓扑快照和同一规则参数应得到确定结果；
- 路径规则必须有测试样例，特别覆盖多段支路、汇合点、并行管和环路。

### 7.3 M3 二维布局引擎

职责：
- 根据拓扑和布局规则生成二维几何；
- 处理主干、支路、节点位置、转折点和排布优化；
- 记录布局参数和优化过程；
- 输出标准 layout.json。

边界：
- 不修改 topology.json；
- 不承担网页交互；
- 不直接依赖 DXF 图层或块的内部表示；
- 不将显示效果当成拓扑正确性的证明。

布局算法需要区分：
- 拓扑约束：哪些对象必须连接；
- 几何约束：端点、角度、间距、交叉等；
- 工艺约束：图纸可读性、标注空间、排板规则；
- 软目标：减少交叉、减少弯折、提高紧凑度等。

硬约束必须优先满足；软目标不能以破坏拓扑、长度或必要间距为代价。

### 7.4 M4 二维排板工作台

首期能力：
- 平移、缩放、适应全图；
- 节点、路径和连接器选择；
- 搜索与定位；
- 图层显示控制；
- 节点拖动；
- 受约束的路径几何编辑；
- 添加和编辑文字标注；
- 撤销、重做；
- 保存为新的 layout_revision。

编辑规则：
- 任何编辑都应生成可追踪的操作记录；
- 编辑器只修改允许编辑的二维字段；
- 拓扑连接、三维长度和源实体属性默认只读；
- 编辑造成的约束破坏必须即时提示，并进入 DRC；
- 不允许编辑器绕过数据层直接改写源 topology.json。

### 7.5 M5 DRC 校验

DRC 不应只是布局引擎的一个函数，而应是独立的工程检查模块。

建议分为五组：
1. 数据完整性：ID 唯一、字段有效、引用完整；
2. 拓扑完整性：节点/边关系、连通分量、端点、环路和遗漏；
3. 几何质量：端点贴合、交叉、重叠、穿节点、最小间距；
4. 工程一致性：3D/2D 长度、路径组成、对象数量和来源追溯；
5. 输出质量：DXF 实体、图层、块属性、单位、坐标及回读一致性。

每条规则至少包含：
- rule_id、名称、版本；
- 适用对象和计算口径；
- 阈值及单位；
- 严重级别：Error / Warning / Info；
- 结果：Pass / Fail / NotApplicable；
- 命中对象 ID；
- 测量值、阈值和证据；
- 是否允许豁免及豁免依据。

豁免必须有记录、责任人/来源和适用范围。不得把一次豁免自动套用到其他车型或工程。

### 7.6 M6 Publish 工程发布

发布不只是“调用 DXF 导出函数”，而是受控的工程交付流程：

1. 锁定本次发布使用的 topology、layout、规则和算法版本；
2. 执行发布前 DRC；
3. 生成 DXF、Excel 和检查报告；
4. 对 DXF 回读，检查图层、块、属性、坐标、长度和实体数量；
5. 对照发布前布局进行几何一致性检查；
6. 生成发布清单，记录文件名、版本、哈希和生成时间；
7. 校验通过后才将文件标记为正式发布。

发布失败时保留失败报告，不覆盖上一份有效交付物。

## 8. 技术实现建议

### 8.1 首期建议：保留现有技术资产

| 部分 | 建议技术 | 原因 |
|---|---|---|
| 工程计算 | Python | 已有展开、优化、DXF 和数据处理代码 |
| 数据交换 | JSON | 现有 topology/layout 已采用，便于离线和跨语言 |
| Web 前端 | HTML + JavaScript，逐步模块化 | 已有单文件 SVG 查看器可复用 |
| 二维渲染 | 首期复用 SVG | 现有查看器已有搜索、定位和点选逻辑 |
| 图算法 | Python 图结构/自有算法 | 需要明确多重边、环路和路径口径 |
| DXF | 复用现有 Python 导出流程 | 保持 R2000、图层和块属性标准 |
| 报表 | 复用现有 Excel 导出 | 避免重复造轮子 |
| 存储 | 首期本地工程目录和 JSON | 单人使用、离线优先，暂不需要数据库服务 |
| 自动化测试 | Python 单元测试 + 浏览器端测试 | 分别验证工程算法和交互行为 |

### 8.2 是否需要 DLL

首期不建议为了架构完整而引入 DLL。

只有满足以下情况之一，才考虑把某个稳定计算核心封装成 DLL：
- 需要被多个 Windows 桌面程序重复调用；
- 性能测试证明 Python 实现确实成为瓶颈；
- 必须与某个原生 CAD SDK 或 C/C++ 库集成；
- 有明确的二进制接口、部署和版本管理需求。

如果只是让网页调用 Python 算法，先采用本地服务或命令行进程接口更简单。DLL 不是业务模块化的必要条件，也不会自动解决数据模型、算法正确性或接口稳定性问题。

### 8.3 运行模式演进

- 阶段 A：本地离线运行，工程目录作为数据包；
- 阶段 B：本机 Web 工作台 + 本地计算服务；
- 阶段 C：可选云端工程存储和任务执行；
- 阶段 D：团队协同、权限、评审和 PLM 集成。

每个阶段都应保持核心数据契约稳定，避免为了部署方式改变业务数据含义。

## 10. 测试策略：用工程样例证明正确性

不能只用“网页能打开”作为验收标准。建议建立分层测试集。

| 测试组 | 必须覆盖的样例 | 验证目标 |
|---|---|---|
| 数据导入 | 正常文件、缺字段、重复 ID、悬空引用 | 导入结果明确、错误可定位 |
| 拓扑 | 单链、多分支、多段支路、汇合点、环路、并行边 | 图关系和路径组成正确 |
| 路径长度 | 多段 Branch 组成的端到端路径 | 连接器到连接器的路径长度口径正确 |
| 布局 | 主干、支路、过路点、隐藏平行管 | 拓扑不丢、几何可追溯 |
| 编辑 | 拖节点、移动路径、撤销重做 | 关联几何更新正确，源数据不变 |
| DRC | 人为注入交叉、间隙、脱开、漏段 | 每条规则能检出并指出对象 |
| DXF | 块、属性、图层、单位、实体回读 | CAD 文件结构和几何符合契约 |
| 回归 | 已确认的地板/IP 等工程样例 | 算法修改不破坏已通过结果 |

每个已发现的真实错误都应转化为一个可重复测试用例。测试数据应保留输入快照、期望结果和规则版本。

## 11. 分阶段实施路线

### P0：冻结概念和数据口径

- 明确 Node、Segment、Branch、Route 的定义；
- 核实现有 topology.json 与 layout.json 的真实字段；
- 明确连接器到连接器路径的计算口径；
- 盘点已有 Python、HTML、DXF、Excel 代码；
- 为关键工程样例建立回归测试。

交付：领域模型说明、数据契约、测试样例目录。

### P1：打通只读工程闭环

- 导入 topology.json；
- 运行现有布局引擎；
- 加载 layout.json；
- 网页查看、搜索和定位；
- 运行独立 DRC；
- 导出 DXF/Excel 并回读检查。

交付：可重复运行的离线只读版本。

### P2：实现受控二维编辑

- 节点拖动与关联路径更新；
- 路径几何编辑；
- 标注；
- 撤销/重做；
- 编辑版本保存；
- 编辑后 DRC 与 DXF 发布。

交付：可编辑的 2D 排板工作台。

### P3：工程项目化

- project.json / manifest；
- 多工程目录；
- 工程版本和操作记录；
- 发布包管理；
- 用户可恢复到历史布局版本。

交付：可管理多个工程的单机工具。

### P4：专业能力扩展

按真实需求依次评估：
- Library 零件库；
- Logic 原理图；
- Integrator 逻辑与物理拓扑匹配；
- CATIA/MCAD 数据接口；
- 制造工艺文件和报表。

### P5：服务化与协同

只有在出现多人使用、远程访问或跨团队交付需求后，再建设：
- 服务端存储；
- 用户和权限；
- 任务队列；
- 协同编辑；
- PLM/企业系统集成。

## 12. 首期验收标准

首期不是以功能数量验收，而是以工程闭环验收。

1. 能读取一份已确认的 topology.json，且不修改源文件；
2. 能生成并展示对应 layout.json；
3. 所有节点、分支、线段和路径具有稳定 ID 和追溯关系；
4. 能区分物理 Branch、基础 Segment 和端到端 Route；
5. 对已定义的拓扑和几何错误能够由独立 DRC 检出；
6. 编辑二维布局不会改变源拓扑和三维长度真值；
7. DXF 导出后能回读验证，且关键实体与布局一致；
8. 同一输入、同一算法版本和参数可重复得到相同结果；
9. 每次发布都有数据版本、规则版本、算法版本和文件清单；
10. 失败时能定位到具体对象和规则，而不是只显示“生成失败”。

## 13. 当前必须确认的架构决策

以下事项不应由开发者自行猜测：

| 决策项 | 当前建议 | 需要验证的内容 |
|---|---|---|
| 源拓扑是否可编辑 | 不可编辑，作为快照 | 外部数据变化时如何重新导入 |
| Route 定义 | 独立于 Branch 和 Segment | 端点类型、环路和多路径的业务口径 |
| 二维编辑是否改变 3D 长度 | 不允许 | 2D 几何与 3D 真值的容差及表达方式 |
| 布局重算如何处理人工编辑 | 不覆盖，要求显式选择 | 局部重算和冲突提示机制 |
| DRC 失败是否允许发布 | Error 阻断；Warning 按规则策略处理 | 每条规则严重级别及豁免机制 |
| 首期运行方式 | 本地离线 | 用户电脑浏览器、Python 运行环境和权限限制 |
| 是否引入数据库 | 首期不引入服务端数据库 | 多工程规模和查询需求出现后再评估 |
| 是否使用 DLL | 首期不需要 | 性能或外部 SDK 集成有实证需求时再决定 |

## 14. 与现有《框架与接口规格》的关系

两份文档承担不同职责：

- 《框架与接口规格》：记录现有文件结构、字段、脚本、DXF 标准、现有功能和待确认事项，属于**现状与接口规格**。
- 本文《总体架构设计》：说明产品定位、业务模块、领域模型、分层、工程流程、技术路线和实施阶段，属于**目标架构建议**。

发生冲突时：
1. 已实测的现有字段和代码行为，以真实文件为准；
2. 用户已确认的工程规则，不得被架构建议覆盖；
3. 本文中的新增建议，未经实测或用户确认，不得直接作为代码默认值；
4. 架构调整应同步更新数据契约、测试用例和实施文档。

## 15. 最终建议

WEBCAD 的核心竞争力不在于网页画得多漂亮，也不在于采用了多少先进技术，而在于：

- 能否正确理解线束拓扑；
- 能否正确识别多段 Branch 构成的工程 Route；
- 能否在二维排板时保持真实工程关系；
- 能否通过独立校验发现问题；
- 能否输出 CAD 工程师可以继续使用和检查的文件；
- 能否让每一个结果都能追溯到源数据、算法和规则。

因此，开发优先级应始终是：

**工程对象定义正确 → 拓扑和路径正确 → 布局正确 → 编辑可控 → DRC 可信 → 输出可靠 → 再扩展项目协同和企业集成。**

这比先搭建一个庞大的平台框架更稳妥，也更符合当前 WEBCAD 已有代码和个人/小团队逐步开发的现实条件。
