# WEBCAD 架构评审反馈与复核

- 日期：2026-11-22
- 评审对象：Muse 对《WEBCAD 总体架构设计》V1.1 的评审，以及 ChatGPT 对 Muse 评审意见的复核
- 结论：采纳 Muse 的核心方向，修正其个别表述和证据边界；架构方案更新为 V1.2

---

## 一、Muse 评审的总体判断

Muse 指出上一版架构在技术分层上基本合理，但把当前项目目标改成了“先做通用 2D 工具”，与现有仓库和《框架与接口规格》不一致。

这一批评成立，而且是上一版最重要的方向性错误。

原项目已经有：
- `topology.json`：已有的 3D 导出拓扑数据；
- 现有布局引擎：从拓扑数据生成二维布局；
- `layout.json`：二维布局结果，也是现有模块间的主要交接契约；
- `viewer-unfold.html`：已有 SVG 查看器；
- 现有 DXF / Excel 导出流程和 DRC 规则。

因此当前工作不是从零设计一个通用画图软件，而是把已经存在的线束二维展开流程做成可编辑的网页工作台。

Muse 建议的 C 方向——保留新方案的分层与扩展点，同时保留现有 `layout.json` 数据入口和真实数据试点——应予采纳。

## 二、逐条复核 Muse 的意见

### 2.1 “不接 3D”与现有数据链路的冲突

**Muse 意见：采纳。**

上一版把“不直接接入 CATIA/3D 系统”扩大成“不使用 3D 导出数据”，导致现有布局引擎、查看器、DXF 导出在当前阶段失去作用。

正确边界：
- 当前不直接连接 CATIA，不解析 STEP/STP，不做三维建模；
- 当前要使用已经导出的 `topology.json`；
- 现有布局引擎继续从 topology 生成 layout；
- 网页编辑器的主要入口是现有 `layout.json`。

这不是“当前接入 3D 软件”，而是“使用已有的 3D 数据处理结果”。

### 2.2 `layout.json` 应作为当前编辑入口

**Muse 意见：采纳，但补充边界。**

对用户打开已有二维布局进行查看和编辑时，`layout.json` 是主要入口，也是编辑器、查看器和 DXF 导出之间的核心交接契约。

但不能把 `layout.json` 解释成整个系统唯一的数据源：
- 布局重算仍需要 `topology.json` 进入现有布局引擎；
- DRC 需要 `topology.json` 与 `layout.json` 对照；
- `topology.json` 是只读源数据快照；
- `layout.json` 是二维布局和编辑阶段的核心契约。

因此更准确的说法是：**layout.json 是当前 2D 编辑链路的核心交接点；topology.json 仍是上游布局计算和工程校验的数据依据。**

### 2.3 首期真实样例与 408 路径 / 409 节点

**Muse 意见：采纳。**

“简单图纸生成”如果不指定真实数据样例，就无法形成可验收任务。首期应以现有地板布局样例为基线：
- `layout.json`：408 paths / 409 nodes；
- 对应源 `topology.json`：477 branches / 527 segments / 469 nodes / 319 runs。

这里需要特别强调：两份文件的统计对象和处理阶段不同，不能要求 477 branches 与 408 paths 一一对应。应验证路径组成、对象引用、拓扑保持和 DRC 结果。

### 2.4 DXF 标准沿用现有规则

**Muse 意见：原则采纳，属性细节需谨慎。**

现有《框架与接口规格》已经记录：
- DXF R2000 / AC1015；
- 毫米单位；
- 6 个既有图层；
- 5 个既有共享块名称；
- 管线使用多段线；
- 导出后先回读核验。

这些应作为当前输出基线，不应在新架构中重新待定或另起一套规则。

但 Muse 的“5 个共享块（带 NAME/FULLNAME 属性）”这句话不宜原样写成所有块都具有相同属性。现有规格对不同块的属性描述并不相同，且明确注明部分 SEGMENT 块细节尚未核实。必须逐块以 `make_dxf.py` 和实际 DXF 为准。

Muse 提到的“409/409 回读 0.0000 mm”也需要对应的测试报告或脚本输出作为证据。当前规格写明的通用验收口径是多段线逐点误差不超过 0.01 mm。不能把单次测试结果直接升级为所有文件的保证。

### 2.5 删除“不得把 3D 数据接入重新变成当前前提”

**Muse 意见：采纳。**

上一版 §14 的这句话与“用户明确确认的需求优先于本文建议”相矛盾，也不应由架构文档替用户决定未来是否接入 3D。

已修正为：
“是否接入 3D 软件、何时接入以及接入深度，由用户确认的需求决定；当前试点使用已有导出的 JSON 数据，不要求直接连接 3D 软件。”

### 2.6 文档版本号不一致

**Muse 意见：采纳。**

上一版文件名仍为 V1.0，正文已经写成 V1.1，确实不规范。本次统一为 V1.2，并同步调整文件名。

## 三、对 Muse 评审本身的评价

### 3.1 做得好的地方

1. **抓住了项目目标偏移，而不是只挑文字。** 这条是最关键的评审价值。
2. **对照了现有规格和真实数据。** 用 408 路径 / 409 节点、topology/layout 的既有关系指出问题，具有可操作性。
3. **提出了可执行的 C 方案。** 不是简单否定，而是保留合理的分层架构并恢复真实试点数据链路。
4. **指出了版本和决策权问题。** 这些属于文档治理问题，应该修复。

### 3.2 需要补充或收紧的地方

1. **“layout.json 是数据入口”需要限定范围。** 对网页编辑器和 2D 模块成立；对整个生成链路不完全成立。布局重算和 DRC 仍依赖 topology.json。
2. **DXF 块属性不能概括成统一的 NAME/FULLNAME。** 应逐个块核对实际定义，未核实的部分继续标记为待验证。
3. **0.0000 mm 回读结果需要证据。** 如果有具体测试输出，应把样例、脚本版本、点数和误差统计写进测试记录；否则保留规格中 ≤0.01 mm 的验收门槛。
4. **应明确“不是通用 CAD 项目”。** C 方案不是在原有线束展开工具之外再做一套通用 CAD，而是将已有线束二维数据工作流做成网页编辑工作台；通用图形编辑能力服务于该工作流。

## 四、对 ChatGPT 上一版方案的自我复核

上一版主要错误：

- 把“当前不直接接入 3D 软件”误读为“当前完全不使用 3D 导出数据”；
- 把“简单图纸生成”理解成从空白画布生成通用图纸；
- 将线束专业数据和已有布局数据推迟到未来阶段；
- 没有把现有 SVG 查看器、布局引擎、DXF 导出和 DRC 当作当前资产；
- 对已有 DXF 规则写成待确认，忽略了规格中已有的实测结论；
- 在 §14 写入了不应由架构文档替用户决定的绝对表述。

这不是局部措辞问题，而是没有先核对现有规格就改变了产品边界。本次已按真实数据链路纠正。

## 五、V1.2 已落实的改动

1. 当前定位改为“已有线束 3D 导出数据的 2D 网页展示、编辑、后处理与工程输出”。
2. 明确区分 topology.json、layout.json 和直接连接 CATIA/3D 软件三件事。
3. 恢复 topology → 现有布局引擎 → layout → 网页编辑/查看 → DRC → DXF 的数据链路。
4. 明确 layout.json 是 2D 编辑链路的核心契约，topology.json 是布局计算和 DRC 的源数据依据。
5. 把地板 408 paths / 409 nodes 作为首期真实样例，并保留源拓扑的统计信息。
6. 明确复用现有 SVG 查看器，不另起炉灶。
7. 明确首期四项编辑试点：拖动节点、调整二维路径、文字标注、DXF 导出。
8. 明确 len_3d、dia 和拓扑连接只读，编辑只作用于二维表达。
9. 沿用现有 DXF R2000、图层、块和回读检查规则，不擅自扩展块属性结论。
10. 修正文档版本号，并删除限制用户未来决策权的绝对表述。

## 六、仍需实测的事项

- 节点拖动时关联路径如何更新；
- 路径编辑的具体交互方式和长度约束；
- 标注如何持久化并映射到 DXF；
- 现有 DXF 各块的逐项属性及 SEGMENT 块真实定义；
- 409/409、0.0000 mm 回读结果对应的原始测试记录；
- 目标浏览器下本地文件读写以及网页调用现有 Python 脚本的可行方式。

这些事项不应靠架构文档猜测，应在 P0/P1 通过真实文件和可重复测试确认。

## 七、最终结论

Muse 的核心评审意见是正确的，尤其是恢复现有数据链路这一点。它的 DXF 属性和回读精度表述需要进一步核实，不能不加区分地全部当作已证实规格。

最终采用的方向是：

**保留 Muse 建议的 C 方向：架构采用模块化和可扩展设计，当前试点仍以已有 topology/layout 数据为基础，优先完成网页 2D 展示、编辑、后处理、DRC 和 DXF 输出。**

本反馈与 V1.2 架构文档配套，作为本轮评审记录。
