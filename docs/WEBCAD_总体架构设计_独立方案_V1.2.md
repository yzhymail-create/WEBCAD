# WEBCAD 总体架构设计（独立方案）

- 文档版本：V1.2
- 日期：2026-11-22
- 状态：架构建议稿，结合《框架与接口规格》及 Muse 评审修订；实施前以真实代码和用户确认的需求为准
- 当前定位：已有线束 3D 导出数据的 2D 网页展示、编辑、后处理与工程输出工具
- 架构原则：当前功能聚焦，数据链路不变，模块边界清楚，未来按需扩展

---

## 0. 核心结论

WEBCAD 当前不是一个从空白画布起步的通用网页 CAD，也不是一个直接操作 CATIA 三维模型的系统。

当前要做的是：

> **把现有线束三维数据处理流程产生的二维展开结果，搬到网页上展示、编辑和后处理，并可靠地输出工程 DXF。**

因此必须区分三个概念：

1. **使用已有 3D 导出数据**：当前需要。系统读取现有的 `topology.json`，并通过现有布局流程产生 `layout.json`。
2. **直接接入 3D 软件或三维模型**：当前不需要。首期不开发 CATIA 插件，不直接操纵 CATIA，不解析 STEP/STP，也不做三维建模。
3. **网页端 2D 编辑与后处理**：当前核心。以现有 `layout.json` 为编辑、查看、校验和导出的主要数据契约。

当前重点是复用已有数据、算法、查看器和 DXF 规则，完成网页编辑闭环。通用绘图能力只做到支持本项目所需的二维对象编辑，不把产品范围扩大成完整通用 CAD。

## 1. 当前范围与未来范围

### 1.1 当前必须实现

| 能力 | 当前具体范围 |
|---|---|
| 数据读取 | 读取现有 `layout.json`；按需读取只读的 `topology.json` |
| 二维展示 | 复用现有 SVG 查看器的渲染、缩放、搜索、定位、弹窗和图层显示能力 |
| 二维编辑 | 在现有布局结果上进行受控编辑，不改变 3D 真值和拓扑关系 |
| 节点与路径操作 | 首期试点包括节点拖动、二维路径几何调整；关联几何更新规则需通过样例验证 |
| 后处理 | 添加文字标注、调整图面表达、必要的图层/显示属性处理 |
| 保存 | 保存编辑后的 `layout.json`，保留源数据和未知字段，避免覆盖布局引擎内部数据 |
| 校验 | 使用现有 DRC 口径，结合 `topology.json` 与编辑后的 `layout.json` 检查 |
| 工程输出 | 复用现有 DXF R2000 导出流程；输出前检查，导出后回读核验 |
| 操作体验 | 选择、拖动、缩放、平移、搜索定位、撤销/重做等必要编辑操作 |

### 1.2 当前明确不做

- 不开发 CATIA 插件，不直接连接或控制 CATIA；
- 不解析 STEP/STP，不做三维建模、三维布线或三维编辑；
- 不重写现有拓扑提取和布局算法；
- 不把现有 `topology.json` / `layout.json` 数据链路替换成一套全新的通用图纸生成数据；
- 不把首期扩展成完整通用 CAD，不做与线束展开试点无关的大量绘图命令；
- 不做企业级账号、多人实时协同、云端项目服务和 PLM；
- 不为了未来扩展提前引入微服务、复杂数据库或 DLL。

### 1.3 未来扩展预留

| 模块 | 未来能力 | 当前处理方式 |
|---|---|---|
| Project | 多工程、工程版本和项目元数据 | 试点阶段轻量处理，不做完整项目管理 |
| Library / Symbol | 连接器、端子、附件、符号和模板库 | 预留 Provider 接口，不拖慢试点 |
| Logic | 电气原理图及电气连接数据 | 预留独立数据模型和入口 |
| Integrator | 原理图与物理线束数据匹配 | 未来独立模块，不改变当前布局契约 |
| 3D / MCAD Connector | 外部三维软件数据导入、同步或联动 | 未来按需增加；不等于当前必须直接连接 3D 软件 |
| Automation | 批量生成、规则和脚本扩展 | 预留命令/规则注册机制 |
| Collaboration | 用户、权限、评审和协同 | 未来按实际使用人数决定 |
| PLM / ERP / MES | 企业系统数据交换 | 未来通过独立适配器接入 |

**原则：未来可以扩展，但当前只实现真实需要的功能。预留接口不等于提前建设空壳模块。**

## 2. 对现有数据链路的定位

### 2.1 当前主数据流

```
已有 topology.json（3D 导出数据，源数据只读）
             │
             ▼
       现有布局引擎
             │
             ▼
       layout.json（2D 布局结果）
             │
       ┌─────┼─────────────┐
       ▼     ▼             ▼
   网页编辑器 查看器       DRC 校验
       │     │          topology + layout
       ▼     │             │
编辑后的     │          检查报告
layout.json  │             │
       │     │             │
       └─────┴──────┬──────┘
                    ▼
             DXF / Excel 等输出
                    │
                    ▼
                回读核验
```

### 2.2 两个数据入口的职责必须分清

- `topology.json` 是上游三维导出数据的只读快照，供现有布局引擎生成布局，并供 DRC 对照源拓扑。
- `layout.json` 是二维布局结果，也是编辑器、查看器、校验和 DXF 导出之间的核心交接格式。
- 用户打开一个已有布局进行编辑时，主要入口是 `layout.json`；需要重新计算布局时，才由 `topology.json` 进入现有布局引擎。
- 网页编辑器不得自行从 `topology.json` 重新发明一套布局算法，也不得将布局引擎内部中间数据当作编辑器契约。
- `layout.json` 中的 3D 长度、直径、节点连接和来源追溯信息是工程真值或源数据属性；编辑器只能修改明确允许的 2D 表达字段。

### 2.3 现有数据样例作为首期验收基线

按《框架与接口规格》记录的真实样例：

| 文件/数据 | 已记录数量 | 用途 |
|---|---:|---|
| 地板 `topology.json` | 477 branches / 527 segments / 469 nodes / 319 runs | 源拓扑与 DRC 对照 |
| 地板 `layout.json` | 408 paths / 409 nodes | 网页展示、编辑和导出试点 |

这些数字属于不同阶段、不同对象口径，**不能要求 477 条 Branch 与 408 条 Layout Path 一一对应**。合并路径、过路点处理、隐藏平行管和其他布局规则都会影响数量。验收时应核对对象追溯关系和规则结果，而不是简单比较数组数量相等。

## 3. 总体分层架构

```
┌─────────────────────────────────────────────────────────────┐
│                    Web 工作台 / 应用层                       │
│ 文件打开｜画布｜工具栏｜搜索定位｜对象信息｜属性/标注面板      │
├─────────────────────────────────────────────────────────────┤
│                    业务模块层                                │
│ 数据适配｜布局调用｜2D 编辑｜查看交互｜DRC｜DXF/报表输出      │
├─────────────────────────────────────────────────────────────┤
│                    领域与数据契约层                          │
│ topology.json（只读源）｜layout.json（核心交接契约）          │
│ 编辑命令｜标注数据｜检查报告｜发布清单                        │
├─────────────────────────────────────────────────────────────┤
│                    图形与计算适配层                          │
│ 现有 SVG Renderer｜几何计算｜选择/捕捉｜DXF Adapter          │
│ 现有布局引擎适配器｜文件读写适配器                            │
├─────────────────────────────────────────────────────────────┤
│                    基础设施层                                │
│ 本地文件｜操作历史｜日志｜配置｜测试样例｜版本迁移            │
└─────────────────────────────────────────────────────────────┘
```

### 3.1 分层职责

| 层 | 职责 | 边界 |
|---|---|---|
| Web 工作台 | 页面布局、工具入口、用户操作流程 | 不直接实现布局算法和 DXF 文件结构 |
| 业务模块 | 数据导入、编辑、查看、校验和输出流程 | 通过统一数据契约协作 |
| 领域/契约层 | 定义源数据、布局数据、编辑数据和引用关系 | 不依赖 SVG DOM 或 DXF 实体 |
| 图形/计算适配层 | SVG 显示、几何操作、现有脚本调用、DXF 读写 | 不擅自改变工程数据含义 |
| 基础设施层 | 文件、日志、测试、配置和历史记录 | 不包含线束专业判断 |

首期不需要微服务化。模块边界体现在代码职责和输入输出，不要求拆成独立部署单元。

## 5. 数据契约与编辑边界

### 5.1 `layout.json` 是当前 2D 模块的核心契约

沿用现有规格的原则：

- 布局引擎产生 `layout.json`；
- 编辑器读取并保存 `layout.json`；
- 查看器只读 `layout.json`；
- DXF / Excel 导出读取 `layout.json`；
- DRC 同时读取 `topology.json` 与 `layout.json`，对照检查；
- 布局引擎内部字段不得被编辑器、查看器或导出器擅自依赖。

现有 `layout.json` 已区分契约字段与布局算法内部字段。编辑器应只依赖规格明确列为契约的字段；对 `projection`、`spines`、`tree`、`slots`、`flips` 等内部字段，不得建立长期依赖。

### 5.2 编辑允许修改什么

| 数据 | 编辑权限 | 说明 |
|---|---|---|
| 2D 路径点列 `points` | 允许，受约束 | 编辑二维图面几何 |
| 节点 2D 坐标 `x/y` | 允许，受约束 | 节点移动后要处理关联路径 |
| 文字标注 | 允许 | 需要定义可持久化的数据结构 |
| 图层/显示属性 | 按明确字段允许 | 不得影响源拓扑 |
| 3D 长度 `len_3d` | 只读 | 不得因二维编辑而改写 |
| 直径 `dia` | 只读 | 源数据属性 |
| 节点连接、Segment 关系 | 只读 | 首期不改拓扑 |
| 源 `topology.json` | 只读 | 不允许网页编辑器覆盖 |

“改长度”在首期应解释为调整二维表达的几何长度，而不是改写 3D 真值。若调整后的二维长度违反既有长度规则，应由 DRC 报告；不能静默篡改 `len_3d`。

### 5.3 编辑数据保存策略

- 优先在现有 `layout.json` 上以向后兼容的新增字段保存编辑结果。
- 标注、编辑记录和必要的编辑元数据应采用明确的独立字段或附属文件，不得混入布局引擎内部字段。
- 保存时保留未知字段、原始对象 ID、字段含义和原有精度。
- 重新运行布局引擎不得无提示覆盖人工编辑；需要明确提示重新生成、保留编辑或放弃编辑。
- `schema_version` 当前仍按现有规格列为待确认事项，不在没有迁移测试前擅自升级或改变旧字段含义。

## 6. 当前网页编辑器设计

### 6.1 先复用现有查看器

现有 `viewer-unfold.html` 已有 SVG 渲染、搜索、定位、缩放、弹窗和图层交互。首期应在它的基础上增加编辑能力，而不是另起炉灶重写一套渲染器。

应尽量复用现有的：
- 全图适配、缩放和平移；
- 搜索与定位；
- 节点/路径点击和信息弹窗；
- 显示名与真实名称的既有处理；
- 图层显示逻辑。

查看器保持只读模式；编辑器在同一渲染与数据模型上增加编辑命令。

### 6.2 首期编辑操作

按现有试点规格，首期围绕四项能力：

1. **拖动节点**：更新节点二维坐标，并按明确规则更新关联路径端点；具体关联几何行为通过样例测试确定。
2. **调整二维路径**：允许编辑路径点列或二维画出长度；不得修改 `len_3d`、直径或拓扑关系。
3. **添加文字标注**：标注必须能保存、重载并导出，不能只存在于浏览器临时 DOM。
4. **导出 DXF**：使用现有导出流程，不能由浏览器另写一套不兼容的 DXF 规则。

后续再根据实际使用反馈增加复制、删除、对齐、捕捉等命令，不为追求“像 CAD”而提前堆叠功能。

### 6.3 编辑器内部机制

- 所有编辑操作通过 Command/Operation 机制执行；
- 支持撤销/重做；
- 选择状态、高亮、缩放和平移属于界面状态，不写入工程几何；
- 编辑后立即更新当前画面，并将变更持久化到数据模型；
- 关键编辑动作应可追溯到对象 ID；
- 不能让 SVG DOM 成为唯一数据源。

## 7. DRC 与工程输出

### 7.1 DRC

继续沿用《框架与接口规格》中的 DRC 原则：只检查、报告，不擅自修复；关键错误阻断正式出图。

当前检查重点包括：
- 源拓扑与布局对象引用完整；
- 节点与路径端点贴合；
- 自环段、断开、孤岛、交叉、共线重叠；
- 非连接节点穿越和节点过近；
- 3D 真值与二维布局长度口径；
- 编辑后是否引入新问题；
- DXF 输出实体与布局数据一致性。

已有阈值、豁免和卡口口径以《框架与接口规格》及真实测试为准。架构文档不重新发明阈值。

### 7.2 DXF 输出标准

沿用现有 `make_dxf.py` 中已经确认的标准，不重新设计：

- DXF R2000（AC1015）；
- 毫米单位；
- 现有 6 个图层及颜色约定；
- 现有 5 个共享块的命名和块属性约定；
- 管线保持现有多段线表达；
- 连接器、节点、分叉、长度等对象沿用当前块/实体映射；
- 先输出临时文件，再回读检查，验证通过后才作为正式输出。

注意：块的具体属性并非可以笼统写成“每个块都有 NAME/FULLNAME”。应逐个以 `make_dxf.py` 和实测 DXF 为准；现有规格已注明部分块细节尚未核实，不得在架构文档中扩大成已确认事实。

当前规格的回读验收口径是多段线逐点误差不超过 0.01 mm。若另有测试记录证明某批样例达到 0.0000 mm，可以作为该次测试结果记录，但不能在缺少测试报告时将其升级为普遍保证。

### 7.3 输出闭环

1. 锁定本次输入的 topology/layout 版本；
2. 执行编辑后 DRC；
3. 生成 DXF / 现有报表；
4. 回读 DXF，核对图层、实体、块属性、坐标和多段线点位；
5. 保存检查报告和输出文件；
6. 校验失败时保留失败报告，不覆盖上一份有效输出。

## 8. 技术实现建议

| 部分 | 当前建议 | 原因 |
|---|---|---|
| 前端 | HTML / CSS / JavaScript | 轻量，符合现有单文件网页基础 |
| 二维渲染 | 复用现有 SVG 查看器 | 已有交互成熟，减少重写风险 |
| 数据 | JSON | 现有拓扑和布局数据已经采用 |
| 几何编辑 | 独立几何与命令模块 | 不把业务逻辑写进 SVG DOM |
| 布局计算 | 复用现有 Python 布局引擎 | 不重复实现已有算法 |
| DXF | 复用现有 Python 导出流程 | 保持 R2000、图层和块标准一致 |
| 保存 | 先采用本地文件方式 | 试点阶段单人/小范围使用，无需服务端 |
| 后端 | 首期不强制 | 只有浏览器无法满足文件或计算需求时再增加本地服务 |
| 数据库 | 首期不需要 | 当前文件式工程流已足够 |
| DLL | 首期不需要 | 不解决当前核心问题 |

若网页端需要调用 Python 脚本，可先通过本地启动器/本地服务/命令行适配器评估，不把 DLL 当作默认方案。具体运行方式应以目标电脑权限和浏览器文件能力实测为准。

## 13. 与《框架与接口规格》的关系

- 《框架与接口规格》记录现有数据结构、脚本、查看器、DXF 标准、DRC 和试点范围，是详细事实与接口依据。
- 本文定义整体分层、模块职责、扩展方向和实施顺序，是目标架构建议。
- 已有实测数据和代码行为优先于架构建议。
- 用户明确确认的需求优先于本文任何建议。
- 是否接入 3D 软件、何时接入以及接入深度，由用户确认的需求决定；当前试点使用已有导出的 JSON 数据，不要求直接连接 3D 软件。
- 未经实测或用户确认的建议，不得直接变成代码默认值。
- 修改数据契约时，必须同步更新测试样例和接口说明。

## 14. 最终建议

WEBCAD 当前应围绕真实的地板线束展开数据，先完成：

**读取现有 layout.json → 网页展示 → 受控二维编辑 → 后处理 → DRC → 复用现有 DXF 输出 → 回读核验。**

`topology.json` 仍是上游源数据和 DRC 对照依据；现有布局引擎继续负责拓扑到二维布局的计算；网页端不重写这部分算法。

架构上保留模块化和扩展接口，未来可接入零件库、原理图、Integrator、3D/MCAD 和协同能力。但这些扩展不应阻塞当前试点。

**当前聚焦真实数据闭环，未来保持扩展空间；不重复造轮子，不把已有成果丢掉，也不提前建设尚无用例的复杂平台。**
