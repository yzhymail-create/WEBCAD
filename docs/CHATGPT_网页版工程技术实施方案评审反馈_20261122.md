## 一、总体评价与核心原则

当前方案选择“已有线束数据链路先行、网页化二维编辑、保留未来平台扩展”的路线是合理的。首期应继续复用现有布局引擎、SVG 查看器、DRC 和 DXF R2000 导出器，不应为了追求通用 CAD 架构而从零重写已有能力。

首期产品应明确定位为：

> 基于现有线束拓扑和二维布局数据的网页工程工作台，支持二维图纸查看、有限编辑、工程校验和 DXF 输出。

当前不做 CATIA 直接连接、不做三维建模、不做通用空白画布 CAD，也不把 Project、Library、Logic、Integrator、协同服务等远期模块作为首期交付前提。

实施过程中坚持以下原则：

1. 原始工程数据与二维显示/编辑数据分离。
2. 3D 拓扑真值只读，二维编辑不得悄悄改变真实拓扑和 3D 属性。
3. 先验证真实数据闭环，再抽象通用领域模型。
4. 每项编辑必须可追溯、可撤销，并能通过工程校验。
5. DXF 输出必须沿用现有标准和回读验证流程，不以屏幕显示正确代替工程正确。
6. 新增字段和规则必须有版本、兼容策略及真实样例验证，不能只在文档中先行假定。

## 二、建议优先修订的工程问题

### 2.1 明确三类核心数据的职责

当前方案将 `layout.json` 定义为编辑器主要入口是合理的，但“唯一交接点”这一表述过于绝对。布局计算和最终工程校验仍需要原始拓扑作为依据。

建议明确：

| 数据 | 工程职责 | 首期读写原则 |
|---|---|---|
| `topology.json` | 原始拓扑、连接关系、3D 属性和来源依据 | 只读，不由网页编辑器改写 |
| `layout.json` | 二维布局、节点位置、路径几何及布局结果 | 作为网页编辑的主要输入和输出 |
| 编辑记录/工程元数据 | 记录编辑来源、修改对象、操作和版本 | 独立管理，避免混淆原始数据与当前几何 |

建议的数据流：

```
topology.json（只读）
       │
       ▼
现有布局引擎
       │
       ▼
layout.json（二维初始布局）
       │
       ▼
网页编辑器（内存副本）
       │
       ▼
edited layout.json（二维编辑结果）
       │
       ├── 原始 topology.json
       ▼
Python 全量 DRC
       │
       ▼
现有 make_dxf.py
       │
       ▼
DXF R2000 + DRC 报告
```

注意：首期不建议为了增加 `schema_version` 而直接修改原始 `topology.json`。可以先在 WEBCAD 工程包装信息或编辑结果中记录格式版本；若确需修改既有数据契约，应先评估所有现有脚本对未知字段的兼容性，并用真实输入做回归。

### 2.2 节点拖动必须定义为关联对象事务

现方案提出同步修改 `nodes[].x/y`、`branches[].points` 和 `pieces[].pts`，方向正确，但还缺少完整的关联更新规则。

一个节点可能连接多条路径；一条合并路径又可能包含多个原始 pieces。只移动节点坐标，或者只修改路径首尾点，都可能造成节点与管端脱开、合并路径几何不一致或段级追溯丢失。

建议把一次拖动定义为一个原子编辑事务：

1. 识别被拖动节点及其稳定标识。
2. 查找所有引用该节点的路径端点和段端点。
3. 生成受影响对象清单。
4. 在临时几何副本上更新节点和关联端点。
5. 同步维护 `branches[].points` 与 `pieces[].pts` 的一致性。
6. 检查重复点、零长度段、端点脱开和几何异常。
7. 通过后提交本次修改；失败则回滚。
8. 将整个事务作为一个 Undo 单元记录。

特别需要明确：不能因为某个中间几何点坐标相同，就把它误判为同一个拓扑节点；节点关联必须依据拓扑标识和段级关系，而不是仅靠坐标猜测。

建议首期先实现节点拖动和关联端点同步，不在同一阶段引入复杂的自动避让或全图重新排布。

### 2.3 “改长度”应先定义工程含义，再决定交互

当前方案中的“改长度”同时可能表示修改端点间距离、改变中间走向、改变二维几何总长或仅修改显示数值。这些不是同一件事。

例如一条路径经过多个固定卡扣，用户要求增加 100 mm，必须明确是移动端点、移动卡扣、增加中间绕行，还是只改变图纸表达。若只改 `len_2d` 数字而不改变几何，图形和长度就会不一致。

建议拆分为：

| 功能 | 实际修改 | 工程要求 |
|---|---|---|
| 路径形状编辑 | 修改二维折线点列 | 重新计算几何长度 |
| 路径长度调整 | 通过受控几何操作改变二维实际长度 | 必须定义固定端点、固定节点和允许移动范围 |
| 3D 真值 | `len_3d`、真实段长及拓扑属性 | 只读，不因二维编辑而改写 |

建议首期先完成节点拖动；路径形状编辑作为下一项；独立的长度调整在几何编辑规则确定后再实施。不要把“输入一个新数值并覆盖 `len_2d`”当成完整的长度编辑功能。

`len_2d` 应由编辑后的几何重新计算，不能仅依赖用户输入值。对修改过的路径，应同时保留原始值、当前值、修改原因和修改状态。

### 2.4 编辑状态不能简单豁免 DRC

当前方案提出用 `edited: true` 让 H2（2D/3D 长度 1:1）不再卡住修改路径。这有可能把用户有意修改和实际错误混在一起。

建议将检查结果区分为：

- 原始布局已有的问题；
- 用户有意修改导致的差异；
- 编辑操作新引入的几何错误；
- 仍然必须满足的拓扑和几何硬约束。

`edited` 只能作为“该对象发生过编辑”的标识，不能自动豁免端点脱开、交叉、自环、断连等规则。H2 是否对某类有意修改路径采用不同口径，应由明确的工程规则决定，并在报告中保留原值、现值、差值及豁免原因。任何豁免不得由编辑器静默生成。

### 2.5 DXF 导出流程需要定义为可操作的交付链路

当前方案采用“网页下载编辑后 JSON，再由本地 Python 调用 `make_dxf.py`”是首期可行路线，但它不是浏览器内一键导出 DXF。

建议首期明确提供两个动作：

- **下载编辑后布局**：导出经过格式检查的 JSON。
- **本地生成 DXF**：由本地工具读取编辑结果和对应原始拓扑，执行全量 DRC，通过后调用现有 DXF 导出器。

为降低用户操作成本，建议配套一个简单的本地启动入口（例如批处理脚本或免安装启动器）。它至少应完成：选择输入文件、确认原始拓扑对应关系、执行全量 DRC、调用导出器、保存 DXF 和报告。具体实现方式应结合用户电脑权限和 Python 环境实测后决定，不要预设必须安装服务或管理员权限。

导出流程应遵循：

1. 输入文件格式及来源检查。
2. 全量 DRC。
3. 生成临时 DXF。
4. 回读临时 DXF，检查实体、图层、块属性及几何。
5. 满足验收条件后才将临时文件作为正式交付文件。
6. 同时输出 DRC 和回读报告。

以后是否移植 JavaScript DXF 导出器，应以本地工作流稳定、DXF 标准完全核实为前提，不应成为首期阻塞项。

### 2.6 标注数据与 DXF 图层应独立于长度标注

用户手工添加的文字可能是工艺说明、装配备注、修改原因或临时提示，与路径长度标注不是同一种业务对象。

建议标注数据至少考虑：

- 稳定 ID；
- 文本内容；
- 坐标；
- 关联对象（可为空）；
- 文字高度；
- 旋转角度；
- 图层或标注类型；
- 是否随关联对象移动。

DXF 是否新增 `ANNOTATION` 图层，需要先检查现有模板、图层标准及下游 CAD 使用方式。当前方案将所有自由文字放入 `LENGTH` 图层不建议直接定为最终规则。首期可以先实现网页内标注保存，DXF 映射规则在核实后冻结。

### 2.7 Undo/Redo 与持久化编辑记录分离

建议区分三种机制：

| 机制 | 目的 | 建议保存位置 |
|---|---|---|
| Undo/Redo | 当前会话撤销和恢复操作 | 内存历史栈 |
| Edit Log | 记录最终工程修改及原因 | 编辑结果元数据或独立记录 |
| Snapshot | 恢复已保存的工程版本 | 文件级版本快照 |

不建议将每一次拖动预览都写入永久 `meta.edit_log[]`。拖动过程可以连续预览，但松开并提交后才形成一个编辑事务。保存时再持久化必要的修改记录。

编辑记录应尽量引用稳定对象 ID，并能说明修改前后值；不要把大段重复几何数据无节制地塞进日志。

## 三、数据安全、来源追溯与版本兼容

建议在实施方案中增加“工程文件来源与保护”要求。

### 3.1 文件来源识别

编辑后的 `layout.json` 应能追溯到它所基于的原始拓扑和布局。建议记录：

- 原始拓扑文件标识或内容哈希；
- 原始布局文件标识或内容哈希；
- 布局生成器版本；
- WEBCAD 编辑器版本；
- 数据格式版本；
- 创建时间和最后修改时间。

这样可以避免把不同车型、不同项目或不同布局版本的数据混用。哈希值用于识别文件内容，不应替代工程对象本身的业务 ID。

### 3.2 格式版本与算法版本分开

`meta.version` 当前表示布局生成器版本，不应同时承担 JSON 格式版本的职责。

建议区分：

- `schema_version`：数据结构格式版本；
- `generator_version`：布局生成算法/脚本版本；
- `editor_version`：编辑器版本；
- `source_revision`：源文件或源工程修订标识。

版本字段的具体命名应在实际代码和现有字段核实后统一，避免同一概念在多个位置重复定义。

### 3.3 原始文件保护

所有编辑均在内存副本或新文件上进行。保存前检查 JSON 可解析性、关键字段完整性、ID 唯一性和数据关系；不得覆盖用户提供的原始 `topology.json` 或原始 `layout.json`。

旧格式文件缺少新增字段时，应按明确的兼容规则读取；遇到未知的高版本格式或关键字段不兼容时，应停止编辑并给出原因，不应静默丢弃字段。

## 四、DRC 与验收口径建议

当前方案采用浏览器快速检查和 Python 全量检查分层是正确的，但两者的规则定义、计算口径和职责还需固定。

### 4.1 检查分层

- 浏览器快速 DRC：针对当前编辑操作及受影响对象提供即时反馈。
- Python 全量 DRC：读取编辑后的布局及原始拓扑，作为最终工程放行依据。
- DXF 回读检查：验证实际导出的 DXF 文件，而不只检查导出前 JSON。

浏览器快速检查不得替代 Python 全量检查。两者如出现结论差异，以全量检查为准，并将差异记录为待修复问题。

### 4.2 建议的验收分类

| 类别 | 关键验收内容 |
|---|---|
| 数据验收 | 408 条路径、409 个节点；关键对象 ID、连接关系及段级数据一致 |
| 编辑验收 | 节点移动后所有关联端点正确同步；撤销/重做准确；保存重开不丢数据 |
| 几何验收 | 无新增端点脱开、自环、非法交叉、零长度段或非预期断连 |
| DRC 验收 | 原始问题、编辑新增问题、明确豁免分别报告；全量 DRC 通过才允许正式出图 |
| DXF 验收 | R2000/AC1015、毫米单位、图层、块、属性和实体几何符合现有标准 |
| 回读验收 | 按现有规格逐点误差不超过 0.01 mm，并核对实体数量、端点和必要属性 |
| 视觉验收 | 全图、放大、搜索定位、弹窗和标注状态均经过截图及人工检查 |
| 兼容验收 | 原始查看器原有搜索、定位、缩放、弹窗等能力没有回归损坏 |

特别说明：实施方案中的“DXF 回读 0.0000 mm”可以作为某次实测结果记录，但不应升级成普遍保证。当前规格的正式几何误差口径是逐点不超过 0.01 mm，除非后续通过明确测试和需求决策提高标准。

## 五、建议调整实施阶段

建议保留 P0–P3 的阶段结构，但重新安排每阶段的交付重点。

### P0：真实数据链路验证

1. 盘点并确认仓库中现有查看器、布局数据、布局引擎、DRC 和 DXF 导出器的真实路径及调用方式。
2. 建立网页入口，加载地板样例 `layout.json`。
3. 复用现有查看器，保持搜索、定位、缩放、弹窗等功能。
4. 验证 408 路径、409 节点及关键数据字段。
5. 建立原始数据基线、截图基线和自动化回归用例。
6. 确认原始文件不会被网页修改。

**P0 暂不拆分 569KB 单文件查看器，也不先做通用 Entity 模型。** 先以低风险方式叠加独立编辑层，确认功能稳定后再决定是否模块化。

### P1：基础编辑闭环

1. 节点选择与拖动。
2. 节点相关路径端点和 pieces 同步更新。
3. 编辑预览、提交和失败回滚。
4. Undo/Redo。
5. 添加、移动、删除文字标注。
6. 保存编辑后的独立 JSON 文件。
7. 编辑前后差异查看。

本阶段不建议同时开发复杂路径长度调整。

### P2：几何编辑与工程后处理

1. 路径形状编辑和几何长度重算。
2. 明确固定端点、固定节点和可移动点的规则。
3. 浏览器快速 DRC。
4. Python 全量 DRC。
5. 本地 DXF 生成入口。
6. DXF 临时文件回读、校验和报告。
7. 在上述能力稳定后，再评估独立的路径长度调整功能。

### P3：试点交付

1. 自动化回归和 Playwright 截图。
2. 浏览器兼容性测试。
3. DXF 在目标 CAD 软件中的打开和继续编辑测试。
4. 用户实际操作验收。
5. 预览部署；用户验收通过后再决定正式发布。

### 中期扩展

通用 2D Entity、Project/Drawing/Sheet、Library、Logic、Integrator、协同、JavaScript DXF Adapter 等按实际业务需求逐项启动。不要在首期并行搭建空壳模块。

## 六、建议补充的风险控制

| 风险 | 可能后果 | 建议控制 |
|---|---|---|
| 节点移动只改部分几何 | 管端脱开、段级数据不一致 | 关联对象事务更新，提交前检查 |
| 直接改写 `len_2d` 数字 | 数值与图形不一致 | 从编辑后几何重算 |
| `edited` 自动豁免 DRC | 隐藏真实工程错误 | 区分编辑差异与硬性错误，豁免必须有规则依据 |
| 编辑后无法找到对应源拓扑 | 错误数据参与 DRC 或导出 | 保存源文件标识/哈希并做一致性检查 |
| 网页检查与 Python 检查口径不一致 | 用户误以为可以出图 | Python 全量 DRC 为最终卡口，差异必须报告 |
| DXF 图层/块属性假定错误 | 下游 CAD 显示或处理异常 | 以真实导出代码和真实 DXF 回读为准 |
| 首期过早模块化 | 增加改造量、拖慢试点 | 先复用现有查看器，稳定后再拆分 |
| 保存覆盖原始文件 | 数据不可恢复 | 原始输入只读，编辑结果另存，保存前校验 |

## 七、需要在开工前冻结的事项

建议把“必须冻结”和“可边做边定”分开，避免要求所有远期需求一次性确认。

### 必须冻结

1. 节点拖动时，所有与该节点关联的路径端点是否同步移动（建议：必须同步）。
2. 二维编辑不改变 `len_3d`、真实段长、`dia` 和拓扑连接（建议：作为硬约束）。
3. 首期编辑结果另存，不覆盖原始文件（建议：作为硬约束）。
4. DRC 最终以 Python 全量检查为准（建议：作为硬约束）。
5. DXF 回读按现有规格逐点误差 ≤0.01 mm 验收。
6. 首期本地 DXF 生成采用何种启动方式，以及目标电脑是否具备可用 Python 环境。
7. 标注首期是否需要导出 DXF；若需要，先确认图层和文字属性标准。

### 可边做边定

- 编辑日志的最终字段命名；
- 标注的高级样式；
- 路径长度调整的交互方式；
- 通用 Entity 的抽象范围；
- 未来服务器保存、登录和协同方案；
- Logic、Integrator、Library 的完整数据结构。

## 八、最终建议
